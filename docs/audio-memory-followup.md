# 音频内存复核

日期：2026-09-27。复核范围是 `apps/web/src/audio`、现有音频内存浏览器脚本和 `docs/audio-validation.md` 中的记录。本次没有启动新的性能采样。

## 结论

未找到足以证明生产代码仍持有整份旧歌曲、重复复制全长 PCM，或未释放波形 Worker 的证据，因此没有修改音频实现。现有 WeakRef 记录显示顺序换歌十次后，旧 `AudioBuffer` 均不可访问，当前歌曲的 `AudioBuffer` 仍可访问；这仅排除了该路径下可见的旧对象强引用，不能证明浏览器原生音频内存或进程 RSS 已回收。

512 MiB 的内存目标仍待验证。按项目现用的浏览器进程组 RSS 代理，已有一次完整首载加十次换歌测得峰值增量 494.0 MiB；其他记录分别为 515.7、625.6 和 744.2 MiB。负载、浏览器启动等待、基线和构建版本不完全一致，因此不能把这些记录当成同条件重复试验，也不能据单次低于门槛判定稳定通过。

## 指标边界

| 指标 | 实际含义 | 对本验收的限制 |
| --- | --- | --- |
| CDP `Runtime.getHeapUsage` | 当前页面 V8 堆统计，另列 backing storage 与 embedder heap | 不覆盖其他 Chromium 进程、GPU 或全部浏览器音频资源；不能单独代表页面内存总量 |
| RSS | 将 CDP 列出的 Chromium 进程 PID 的 `ps` RSS 相加 | 包含 renderer、GPU、音频服务、解码器和缓存；共享页可能在多个进程的 RSS 中重复计数。about:blank 差值是观察页面增量目标时现用的过程级代理，不是页面私有内存 |
| macOS `footprint` | 系统按进程树采集的物理 footprint，可区分部分共享与私有页及页面状态 | 与 RSS 计数口径不同；已有对齐记录按 0.5 秒采样，漏过约 153 ms 后的 RSS 瞬时峰，不能拿其 400.8 MiB 增量替代 512 MiB RSS 目标 |
| `WeakRef` 存活探针 | 页面代码还能否访问被弱引用的包装对象 | 能检查特定 JS 引用链，不能证明 AudioContext、解码器、分配器或 GPU 已归还内存 |

ROADMAP / PLAN 写的是“页面增量”，并要求计入皮肤解码及可测 GPU 部分；现有实验以整组 Chromium RSS 对 about:blank 基线作差。这个代理覆盖面较广，但不等于页面私有内存，也会重复计算共享页。因而记录只能说明当前浏览器进程组增量，不能声称取得了精确的页面专属 footprint。

## 源码审计

- `LatestDecodeQueue` 一次只运行一个不可取消的 `decodeAudioData`；解码在途时只保留最新等待候选。结果过期后被丢弃，不会接纳旧歌曲。
- 新选曲和 `AudioTransport.dispose()` 会清空当前 `AudioBuffer` 引用、停止播放节点，并终止临时波形 Worker。当前歌曲持有一份供播放的 `AudioBuffer` 是预期行为。
- `WaveformWorkerClient` 每轮至多复制 512 个基块并转移给 Worker；在 300 秒、48 kHz、双声道负载中，每块为 3,600,384 字节（约 3.43 MiB）。波形总复制输入受 128 MiB 限制，摘要最多 1 MiB；任务完成、替换或卸载时关闭 Worker。当前实现没有整段 PCM clone。
- `decodeAudioData` 分离传入的编码 `ArrayBuffer`。探针中若包装对象仍在但 `byteLength` 为 0，不能把它算作仍持有整份编码音频。

## 证据与缺口

完整首载加十次换歌的对齐 RSS 记录峰值增量为 494.0 MiB，11 个波形就绪采样首末增加 10.8 MiB；一轮有限样本的上升趋势既不能证明泄漏，也不应被忽略。该次对齐 footprint 增量为 400.8 MiB，但低频采样没有覆盖 RSS 瞬时峰。更早完整换歌记录的 RSS 增量为 625.6 MiB；单曲分阶段记录相对空白基线为 515.7 MiB。此前 744.2 MiB 记录的基线样本还受到音频服务启动时点影响。各结果与限制详见 [`audio-validation.md`](audio-validation.md) 及其链接的原始 JSON。

弱引用脚本使用了实际生产页面和 300 秒双声道 WAV，但没有加载谱面或播放音频；因此未检查播放节点结束时的原生对象回收，也没有为页面内存预算提供数值。RSS 阶段脚本以 100 ms 采样，可能漏过更短的尖峰；单曲阶段试验也不能代替十次连续换歌负载。最新一次完整 RSS 低于门槛，但已有超过门槛的同类记录，且这些运行并非同一构建、同一基线条件下的可比重复测量。

后续若关闭此项，应先固定“页面增量”采用的进程范围和基线窗口，再对当前生产构建做一次完整应用/皮肤就绪后的单曲导入加十次顺序换歌采样，并保存逐进程 RSS、采样错误和构建哈希。若确认需要用系统 `footprint` 辅助解释，应将其作为独立指标报告，不与 RSS 门槛互换。本轮没有新归因或能改变结论的证据，因此不把重复 RSS 采样当作改进；512 MiB 页面增量目标仍待验证。
